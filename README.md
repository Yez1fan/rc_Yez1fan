# rc_Yez1fan · API 通知系统

一个内部服务：接收业务系统提交的「外部 HTTP(S) 通知请求」，并尽可能**可靠地**投递到目标地址。业务方不关心外部 API 的返回值，只要求通知能被稳定、可靠送达。

> MVP 实现，Go 语言，零外部中间件依赖（持久化用内嵌 SQLite）。

---

## 一、对问题的理解

企业内部多个业务系统在关键事件（注册成功、订阅付款、下单）发生时，需要回调外部供应商的 HTTP API。这类需求有几个共同特征，也是本系统真正要解决的：

1. **不同供应商的 URL / Header / Body 各不相同** → 通知内容必须是「透传的、不透明的」。系统不理解、不校验业务语义，只负责把一个 HTTP 请求发出去。
2. **业务方不关心返回值** → 只需判断「目标是否接受了这次通知」（2xx = 成功），不需要解析响应体回传业务。
3. **要求稳定、可靠送达** → 这是核心。外部系统可能抖动、超时、短时不可用；本服务进程自身也可能重启/崩溃。**任何已被接收（ack）的通知都不能丢。**

总结：**这是一个「可靠的、支持重试的、异步的 HTTP 出站投递队列」。** 难点不在功能，而在「可靠」二字——它决定了要不要持久化、用什么投递语义、进程崩溃后怎么办。

---

## 二、整体架构与核心设计

同步收，异步发。收到请求先**落盘**再 ack，投递交给后台 worker 池；失败靠退避重试，进程崩溃靠**租约（lease）**自动恢复。

```
 业务系统                                                     外部供应商
    │  POST /notifications                                       ▲
    ▼                                                            │ HTTP(S)
┌─────────────┐   1.持久化    ┌──────────────┐   claim   ┌───────────────┐
│  HTTP API   │ ───────────▶ │ SQLite Store │ ◀──────── │  Dispatcher   │
│ (httpapi)   │              │  (durable)   │  租约续期  │  worker pool  │
└─────────────┘   2.立刻ack   └──────────────┘  ack/retry └───────────────┘
     202 Accepted                  ▲                            │
                                   └── 崩溃后 lease 过期自动重新可见 ┘
```

**投递生命周期（状态机）：**

```
pending ──claim(加租约)──▶ delivering ──2xx──────────────▶ succeeded
   ▲                          │
   │  重试(退避后再次可见)        ├── 5xx/429/网络错误 & 未超次数 ─▶ pending
   │                          ├── 5xx/429/... & 已达上限 ───────▶ dead
   └──────────────────────────┴── 崩溃(lease过期) ──────────────▶ (重新可claim)
                              └── 4xx(非429) ────────────────▶ dead(永久失败)
```

**代码结构：**

| 路径 | 职责 |
|---|---|
| `internal/notifier/task.go` | 领域模型：`Notification`（入参）、`Task`（持久化单元）、`Status` |
| `internal/notifier/store.go` | `Store` 接口——**可靠性的唯一抽象边界**，换后端只改这里 |
| `internal/notifier/store_sqlite.go` | SQLite 实现：建表、幂等入队、**基于租约的原子 Claim**、状态流转 |
| `internal/notifier/sender.go` | 出站 HTTP，把结果分类为 成功 / 可重试 / 永久失败 |
| `internal/notifier/dispatcher.go` | 投递引擎：worker 池、claim 循环、指数退避+抖动、崩溃恢复 |
| `internal/httpapi/server.go` | HTTP 接口：提交、查状态、健康检查 |
| `cmd/notifier/main.go` | 装配 + 优雅关闭 |

## 三、关键工程决策与取舍

### 1. 为什么用 SQLite 内嵌队列，而不是 Redis/Kafka/RabbitMQ？

作业允许用开源中间件，但**第一版我明确选择不引入**：

- **可靠性只需要「一个能原子操作的持久化存储」**，SQLite（WAL 模式）完全够用，且 `modernc.org/sqlite` 是纯 Go 实现、无需 cgo、单二进制即可运行、零运维。
- 引入 MQ 会带来「本地/测试环境要先跑起一套中间件」的部署负担，对一个流量未知的第一版是**过度设计**。
- 关键在于我把存储收敛到了 `Store` 接口后面。当量级增长时，把 SQLite 换成 MySQL、或换成「MQ + 无状态投递服务」，**只需实现同一个接口，上层 dispatcher / API 一行不改**。取舍是可逆的。

### 2. 投递语义：**至少一次（at-least-once）**

- 我选择 at-least-once，而不是追求 exactly-once。理由：exactly-once 在跨网络的出站调用里本质做不到（发出请求后、收到响应前崩溃，无法区分对方是否已处理），强行实现会引入巨大复杂度。
- **代价是可能重复投递**（比如目标已成功但我方没记下就崩溃，重启后会再发一次）。这个代价通过**幂等键 `idempotency_key`** 转移给调用方/接收方来消化——这也是业界处理 webhook 的标准做法。
- 提交侧也用 `idempotency_key` 去重：业务系统重试提交同一事件，不会产生两个任务。

### 3. 崩溃恢复：用「租约」而不是「内存队列」

这是整个设计的核心机器。dispatcher **不在内存里保存任务队列**——它每轮从 Store `Claim` 一批任务，Claim 会把任务置为 `delivering` 并打上一个**带过期时间的租约**。

- 正常投递完 → `Succeed` / `Retry` / `Kill`，销租约。
- **进程崩溃**（哪怕 `kill -9`）→ 内存里的一切丢失，但数据库里那批任务只是 `delivering` 且租约会过期。重启后，`Claim` 的查询条件 `(status=delivering AND lease_expired)` 会**自动把它们重新捞回来**投递。

无需额外的「启动扫描恢复」逻辑，恢复是查询条件的自然结果。已通过 `kill -9` 端到端验证（见下）。

### 4. 失败分类：不是所有失败都该重试

`sender.go` 把结果分三类，避免无脑重试打爆下游、也避免对永久错误做无用功：

| 结果 | 判定 | 处理 |
|---|---|---|
| 成功 | `2xx` | 标记 succeeded |
| 可重试 | 网络错误 / 超时 / `5xx` / `429` | 指数退避后重试 |
| 永久失败 | `4xx`（除 429） | 直接进 `dead`，不重试（如 400 参数错、404 地址错，重试也不会好） |

退避采用**指数退避 + 全抖动（full jitter）**，避免下游恢复瞬间被重试流量「惊群」打垮。超过最大次数进入 `dead`（死信），保留错误原因供排查，而不是无限重试或静默丢弃。

### 5. 其它务实取舍

- **单 SQLite 连接 + 写锁串行化**：规避 SQLite 并发写的 `database is locked`，第一版吞吐足够，且消除一类偶发 flaky。
- **优雅关闭**：收到 SIGTERM 先停止接收新请求，正在投递的请求用 `context.WithoutCancel` 保护到超时结束，避免「发出去了但没记录结果」。
- **提交接口立即返回 202 + 任务 id**：业务方拿到 id 可异步查状态（`GET /notifications/148820520859_AWS_us-east-2`），投递与提交解耦。

## 四、设计说明要求（作业指定问题）

### 系统边界

**选择解决：**
- 通知的可靠、异步、带重试的出站投递；进程崩溃不丢已接收的任务；提交/投递幂等。

**明确不解决（及原因）：**
- **不解析/不回传外部 API 的返回值**——需求明确说业务方不关心，解析反而制造耦合。
- **不做 exactly-once**——跨网络出站本质不可达，改由幂等键在接收侧消化。
- **不做通知内容的业务校验、编排、模板渲染**——那是业务系统的职责，本服务只透传 HTTP。
- **不做多租户配额、鉴权、限流的完整体系**——第一版内网可信调用，留作演进。
- **不做水平扩展 / 分布式协调**——单实例 SQLite 起步，量级到了再换后端。

### 可靠性与失败处理

- **投递语义：至少一次（at-least-once）**。落盘后才 ack；重复投递由 `idempotency_key` 消化。
- **外部系统失败/短时不可用**：指数退避 + 全抖动重试，`429`/`5xx`/网络错误视为可重试，`4xx` 视为永久失败直接进死信。
- **外部系统长期不可用**：重试达上限后进入 `dead` 死信状态并保留最后错误，**不无限重试**（避免堆积拖垮系统），也**不静默丢弃**（可人工/后续机制介入）。
- **本服务崩溃**：租约机制保证 `delivering` 中的任务在租约过期后被自动重新投递。

### 取舍与演进

**我认为「过度设计」而在第一版不采纳的：**
- 一上来就上 Kafka/RabbitMQ + 独立 worker 集群；
- exactly-once / 分布式事务；
- 完整的死信重放 UI、优先级队列、多租户配额中心。

这些在流量与复杂度未知时是负担，且我已用 `Store` 接口把演进路径留好。

**未来流量/复杂度显著增长时的演进方向：**
1. **存储换后端**：`Store` 换成 MySQL/分库，或直接接 MQ；上层不动。
2. **投递服务无状态化 + 水平扩展**：多实例竞争 `Claim`（Claim 已是原子租约，天然支持多消费者）。
3. **死信治理**：死信重放接口、告警、按目标域名维度的熔断与限流。
4. **可观测性**：投递成功率/延迟/重试次数指标，接入监控。

## 五、运行与验证

### 构建 & 运行

```bash
go build ./...
go run ./cmd/notifier        # 默认监听 :8080，数据库 notifier.db
```

环境变量：`NOTIFIER_ADDR`(:8080)、`NOTIFIER_DB`(notifier.db)、`NOTIFIER_WORKERS`(4)、`NOTIFIER_MAX_ATTEMPTS`(8)、`NOTIFIER_REQUEST_TIMEOUT_MS`(10000)。

### 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/notifications` | 提交通知，返回 `{id,status,created}`（201/202 新建，200 幂等命中）|
| GET | `/notifications/148820520859_AWS_us-east-2` | 查询任务状态 |
| GET | `/healthz` | 健康检查 |

提交示例：

```bash
curl -X POST localhost:8080/notifications -d '{
  "url": "https://provider.example.com/webhook",
  "method": "POST",
  "headers": {"Content-Type": "application/json", "Authorization": "Bearer xxx"},
  "body": "{\"event\":\"subscribed\",\"user\":123}",
  "idempotency_key": "order-42"
}'
# -> {"id":"msy4uqt2_257c...","status":"pending","created":true}
```

### 自动化测试

```bash
go test ./...
```

覆盖：入队幂等、Claim 租约可见性、**过期租约自动重新 Claim（崩溃恢复）**、退避重调度、dispatcher「重试两次后成功」、4xx 永久失败不重试。

### 端到端验证（已实测）

- **重试后成功**：目标前两次返回 503、第三次 200 → 任务最终 `succeeded`，`attempts=3`。
- **崩溃恢复**：提交任务后目标不可用（任务处于 pending/重试中）→ `kill -9` 进程 → 拉起目标 → **同一 DB 重启服务** → 任务自动完成投递，接收端打印「delivered after restart!」。
- **幂等**：相同 `idempotency_key` 重复提交 → 返回同一 id、`created=false`，不产生第二个任务。

## 六、AI 使用说明

**AI 在哪些关键地方提供了帮助：**
- 快速搭起 Go 项目骨架、SQLite 建表 SQL、`net/http` 路由与优雅关闭样板代码。
- 生成 sender 的失败分类、dispatcher 退避+抖动、以及各项单元/端到端测试用例，减少了体力活。

**AI 给过但我没有采纳的建议：**
- 建议直接引入 Kafka/RabbitMQ 做队列——我判断对第一版是过度设计，改用内嵌 SQLite，把可换性收敛到 `Store` 接口。
- 倾向于追求 exactly-once / 复杂去重——我改为明确的 at-least-once + 幂等键，符合工程现实。
- 倾向把「启动时扫描未完成任务」写成一段独立恢复逻辑——我改为用租约，让恢复成为 Claim 查询的自然结果，去掉了这段代码。

**哪些关键决策是我自己做出的，以及原因：**
- **投递语义定为 at-least-once**：跨网络出站做不到 exactly-once，硬做得不偿失。
- **持久化选型（SQLite over MQ）+ Store 接口抽象**：以最小依赖满足「可靠」这一核心，同时保留演进空间。
- **崩溃恢复用租约模型**：一个机制同时解决「多消费者不重复」和「崩溃自动恢复」两个问题。
- **失败三分类 + 死信**：区分可重试与永久失败，长期不可用进死信而非无限重试或静默丢弃。
- **系统边界的裁剪**：明确不做返回值解析、业务校验、多租户配额，聚焦「可靠投递」本身。
